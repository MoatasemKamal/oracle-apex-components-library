# Creative theme templates: List Templates and Region Templates

`theme-templates/` holds **native APEX templates**, not plug-ins: List Templates for the
native List region and navigation lists, and Region Templates that frame any native region
(Classic Report, Interactive Report, Form, Chart, Cards, Static Content). A developer picks
them in **Appearance > Template** (regions) or **List Template** (lists), and turns
variants on with **Template Options**, exactly like Universal Theme's own templates.

They are the creative counterpart of Universal Theme: every template must be
recognisably **not traditional**, using at least one of the Next Collection directions
(`next-collection.md`): `motion`, `depth`, `bold`, `smart`.

## Folder layout

```
theme-templates/<slug>/
  template.json              metadata, template options, list attribute labels
  parts/                     the template HTML, one file per template field
  files/amc-tpl-<slug>.css   required; .js optional (loaded as Static Application Files)
  examples/preview.json      preview samples
  examples/*.apx.md          APEXlang usage example
  README.md, dist/           generated by tools/build-templates.mjs (never edit)
```

Commands (from the skill root):

```bash
node tools/new-template.mjs <slug> <list|region> "<Display Name>"   # scaffold
node tools/build-templates.mjs [--only <slug>]                      # validate + emit
node tools/preview-templates.mjs [--only <slug>]                     # preview/templates[-slug].html
node tools/apexlang-check.mjs --apexlang <apexlang skill root>      # formatter structure check
```

## template.json

| Field | Notes |
|---|---|
| `kind` | `list` or `region` |
| `name` | Shown in the Template select list, e.g. `AMC Orbit Launcher`. No `( ) { }`. |
| `staticId` | `AMC_TPL_<NAME>`; never change it after release |
| `version`, `minApexVersion` | semver; `23.1` unless a gated feature is used |
| `direction` | `motion`, `depth`, `bold` or `smart` |
| `description` | one sentence |
| `useFor` | which native regions or lists it is meant for |
| `helpText` | becomes the template comment: usage, options, keyboard and reduced-motion behaviour |
| `attributes` | lists only: `{ "a01": "Description", "a02": "Badge" }`, labels for List Entry attributes |
| `landmarkType` | regions only: `region` (default), `complementary`, `form`, `navigation`, `search` |
| `templateOptions` | `[{ staticId, name, cssClass, sequence, help }]`; `cssClass` is one `amc-T...` class styled in the CSS |
| `defaultOptions`, `presetOptions` | lists of option `cssClass` values |
| `source` | when adapting MIT work: `{ url, author, license }` |

## Parts and substitutions

Only plain `#TOKEN#` substitutions are used (no template directives), so the same markup works
from APEX 23.1 on. The build rejects unknown tokens.

**Region template** (`parts/region.html`, required tokens `#TITLE#`, `#BODY#`, `#SUB_REGIONS#`,
`#REGION_STATIC_ID#`, `#REGION_CSS_CLASSES#`, `#REGION_ATTRIBUTES#`): also `#ICON_CSS_CLASSES#`
and button positions `#CLOSE# #EDIT# #HELP# #DELETE# #CHANGE# #COPY# #CREATE# #EXPAND# #NEXT#
#PREVIOUS#`. Pattern: `aria-labelledby="#REGION_STATIC_ID#_heading"` plus
`<h2 id="#REGION_STATIC_ID#_heading">#TITLE#</h2>`. Hide empty button bars with `:empty`
and an unset icon with `.fa:not([class*="fa-"])`.

**List template**: `before.html` (must carry `#COMPONENT_CSS_CLASSES#`; may use `#LIST_ID#`),
`after.html`, `current.html`, `noncurrent.html`, optional `between.html`,
`first-current.html` / `first-noncurrent.html`. Entry tokens: `#TEXT#`, `#TEXT_ESC_SC#`,
`#LINK#`, `#IMAGE#`, `#IMAGE_ALT#`, `#ICON_CSS_CLASSES#`, `#LIST_ITEM_ID#`,
`#PARENT_LIST_ITEM_ID#`, `#LIST_STATUS#`, `#A01#`..`#A20#`.

**Sublists** (one level, for menus and side navigation): add all of
`current-with-sublist.html`, `noncurrent-with-sublist.html`, `sublist-before.html`,
`sublist-current.html`, `sublist-noncurrent.html`, `sublist-after.html`. APEX renders the
parent "with sublist" entry, then sublist-before, the child entries, then sublist-after, so the
parent entry leaves its `<li>` open and `sublist-after.html` closes it (`</ul></li>`).

Attribute values chosen by the developer (for example a01 = `wide`) may go into a class
name (`amc-TBento-item--#A01#`) when the help text lists the allowed values and the CSS
ignores unknown ones. Never put a substitution into a `style` attribute.

## Rules

- Everything in `native-look-contract.md` and `next-collection.md` "Shared conventions"
  applies: `--ut-*` variables with literal fallbacks only inside `var()`, only `amc-` class
  selectors (block name `amc-T<Name>`), logical properties, visible focus, complete at rest,
  full reduced-motion and forced-colors handling, touch has no hover-only content.
- **Region templates frame native content; they never restyle it.** Keep the body on a
  readable surface, never `overflow: hidden` on the body (menus, date pickers and IR
  actions must not be clipped; use `overflow-x: auto` if needed), keep the body free of
  transforms (a transformed ancestor breaks `position: fixed` popups), and make every
  template work around a Classic Report, an Interactive Report, a Form, a Chart and text.
  Decorative 3D belongs on the frame, header or backdrop, not the body.
- **List templates** render real links: `<a href="#LINK#">` with `aria-current="page"` on the
  current entry, `aria-hidden="true"` on decorative icons, keyboard reachable in DOM order.
  Navigation-style lists wrap in `<nav aria-label="...">` only when they are standalone
  (the List region can also be used inside a nav).
- **JavaScript** only when CSS cannot do it: ES5 IIFE, `window.amcTpl<Name>` guard,
  delegated listeners on `document` so refreshed regions keep working, `textContent` only,
  `requestAnimationFrame` throttling, nothing moves under reduced motion, and every
  template renders completely without JS.
- One CSS file per template; no global selectors, no `!important` outside reduced-motion
  and forced-colors blocks.
- 3 to 6 template options per template that give real variants (color, density, layout,
  motion intensity), not trivial toggles.

## Living Templates (direction `living`)

Templates that go beyond appearance: they **understand their content or their user** and
adapt. Nothing like this exists in Universal Theme, Bootstrap or the effect libraries, which
only draw frames. A living template must still render completely without JavaScript and
look correct as a plain template; the intelligence is an enhancement.

Kinds of intelligence:

- **Content-aware (region templates):** read the native content inside the body, most often
  a report table, and add meaning: totals, a chart of the same rows, freshness of the data.
  Read cells with `textContent`, parse numbers locale-safely (strip group separators and
  currency, accept `,` or `.` decimals by position), and never change the native markup
  itself; add your own elements beside it.
- **User-aware (list templates):** adapt to how this person uses the app: frequency and
  recency of use, time of day or period of month, pages visited. State lives in
  `localStorage` / `sessionStorage` only, always inside `try/catch`, keyed
  `amc-tpl-<slug>:<appId>:<listId>`. App and page come from `apex.env.APP_ID` /
  `apex.env.APP_PAGE_ID` when present, otherwise `location.pathname`. Nothing personal leaves
  the browser, and each template offers a visible way to reset what it learned.
- **Behaviour-aware (region templates):** change how the page behaves for focus or
  personalisation (focus mode, density, arrangement), with state kept per user and page.

Rules on top of the general ones:

- Re-run after partial page refresh: `if (window.apex && apex.jQuery) apex.jQuery(document).on("apexafterrefresh", handler)`
  plus a `MutationObserver` on the body as a fallback. jQuery-triggered events do not reach
  `addEventListener`.
- Announce computed changes politely (`aria-live="polite"`), give generated charts
  `role="img"` and a text summary, and give every control a real `<button>` with
  `aria-pressed` / `aria-expanded`.
- Guard every APEX API (`apex.region(id)?.refresh`) so previews and older releases do not throw.
- English UI strings live in the template parts (or `data-` attributes on the wrapper) so
  developers can translate them there; list them in `helpText`.
- Prove the logic, not only the look: the preview samples must exercise the behaviour, and the
  author checks results by script (for example that the computed total of the preview
  report is 68,530).
